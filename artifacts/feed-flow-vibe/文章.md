# 一条知光 Feed，背后其实是三条流水线

用户看到的只是一列向下滚动的卡片，但服务端真正解决的是三个同时发生的问题：内容怎么排、下一页怎么稳定、变化怎么及时传播。

如果每次都从 MySQL 里联表、排序、分页，再逐条查询点赞和收藏，逻辑很直观，却会把读压力、排序成本和用户状态耦合在一次请求里。知光当前的实现把它拆成三条流水线：有序候选索引、分层缓存与事件投影。

第一条是“排序流水线”。热门、作者主页和关注流不直接把完整帖子塞进排行榜，而是在 Redis ZSet 里只保存帖子 ID 与 score。作者主页的 score 是创建时间；热门榜的 score 是互动强度经过时间衰减后的结果；关注流则合并普通作者的 inbox 与大 V 的作者索引。ZSet 本身保持顺序，请求只需按 score 向后读取候选。

第二条是“读取流水线”。所有 Feed 入口最终复用 `readPage`：先查页面快照；未命中时，从 ZSet 取三倍候选，批量加载帖子片段，按访问者身份过滤，凑出一页。页面缓存只记“哪些帖子、什么顺序、下一游标”，完整卡片内容拆到独立片段缓存。这样一篇帖子更新时，不需要复制改写所有页面。

游标不是页码，而是一个位置：排序类型、榜单版本、上一个 score 与 postId。时间相同或热度相同的帖子用 postId 打破平局。热门榜每分钟生成一个新版本，但用户继续翻页时沿用旧版本，避免榜单变化造成重复或跳项。

页面快照也不会把所有内容冻死。服务端在 hydrate 阶段重新检查可见性，并批量读取点赞数、收藏数、当前用户是否已操作。公共页面顺序可以共享，用户私有状态则在最后一刻补上。

第三条是“变化传播流水线”。发布、修改、删除和关注变化不直接在请求线程里更新每一份 Feed，而是把事件写入 Outbox。Canal 把数据库变化送到 Kafka，消费者再重建 Redis 投影。消费者收到事件后不盲信旧快照，而是重新读取数据库当前状态，保证投影最终以数据库事实为准。

关注流最有意思。普通作者粉丝量有限，发布时把帖子推入每个粉丝 inbox，读时很快；大 V 粉丝太多，如果也逐个推送，写放大会非常大，所以只在读时拉取大 V 的作者索引并与 inbox 合并。这是一种按作者规模切换的推拉混合。

热门榜则把最近 30 天、最多 2 万篇候选每分钟重新计算。点赞权重 3、收藏权重 5，再除以随时间增长的衰减项。新内容有机会冒头，老内容需要更强互动才能留下。榜单版本写进游标，排序变化和翻页稳定性因此被解耦。

最终，前端只做一件简单的事：把 `nextCursor` 带回接口，把返回的 items 追加到瀑布流。复杂性被留在后端三条流水线里。

这套 Feed 的核心不是“缓存越多越快”，而是把稳定的顺序、可复用的内容和随用户变化的状态分开处理：索引决定看什么，缓存决定从哪里拿，投影决定变化如何到达。
